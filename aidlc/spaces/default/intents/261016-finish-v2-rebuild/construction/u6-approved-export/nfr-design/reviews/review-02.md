> R-01 Reviewer note: §4.2 now gives U6's keyring its own `generation` rule: it starts at 1, rises with every rotation and retirement, and accepts 1 to 2,147,483,647. U2's 1 to 3 range stays a class-level setting. §13 adds a rotate/retire-more-than-three-times test. I checked the built `ControlKeyring`: its tests use `__new__`, `ring.filename`, `ring._write` and `ring.rotate`, all of which the design keeps.

> R-02 Reviewer note: D15 adds an `InteractiveGate`: at most two interactive Notion operations per process and one per connection, and any more fail at once. That leaves at least six of the eight admission slots free. I checked `ControlAdmission`, which has no queue and rejects with 503. The failure table, §5, §6 and the §13 test now carry the bound. See the new finding on connections that do not exist yet.

> R-03 Reviewer note: D16 and the §7 revocation rule separate a candidate token (INVALID_TOKEN, nothing stored) from the stored token. A 401 on the stored token revokes only by compare-and-set on the revision the operation opened, and it is discarded once the revision has moved. Both races have tests in §13.

> R-04 Reviewer note: §4.6 now deletes the key file only after every refusal check has passed, including the acknowledged database stop. One unlink is the deciding step, and the folder is renamed last. It says what happens if the unlink or the rename fails. U6's preservation is called a new destructive step. I compared this with the order of checks in `archive_owned` and it matches. A refused-preservation test is listed.

> R-05 Reviewer note: §4.5 and §5.3 name the two operator-only functions and the schema owner role that alone can execute them. `token_key_counts()` is the only function shared with the runtime role. D13's wording and the test list are adjusted.

> R-06 Reviewer note: The snippet in §6.1 puts token opening and client creation inside the `try`. It catches only `Exception`, which includes the deadline's `TimeoutError`. Outside cancellation, `KeyboardInterrupt` and `SystemExit` pass through.

> R-07 Reviewer note: The marker is created only if absent. Rotation skips and reports tokens under a missing version. A replace seals with the new revision, and the store function sets that revision under the expected one in one step (§4.1, §4.5).

> R-08 Reviewer note: The block-limit answer is identified by 403 `restricted_resource` with `additional_data.block_limit = block_creation`, read from the structured field and not from message text. The fake answers the same way. The row sits before the generic 403 row.

> R-09 Reviewer note: §10 and the failure table now say an accepted export waits only while the approving session lasts. I checked the built policy: sessions are 900 seconds (`control_policy.session_seconds`) and `fresh_expiry` caps at 3600. The 24-hour bound stays as a backstop.

> R-10 Reviewer note: §14 now supersedes the NFR4.10 "Rendered copy retention" row as well as the NFR1.5 sentence.

> R-11 Reviewer note: §9.2 says what happens when the pace reservation still fails after the runner's retries: the operation ends as could-not-check, with no retry loop. An abandoned slot is left used on purpose. §3 defines the configure receipt: it holds no token, no token digest and no salted digest.

> R-12 Reviewer note: The inventory now lists `GuardedTransport`, `InteractiveGate`, `ExportLane` and `NotionSession`. The pace record and its slot reservation appear under `ExportStore`.

### Summary

All twelve prior findings are fixed, and the revisions for custody, admission, revocation and preservation hold up against the built code. One Major gap remains: a first-time owner's token check has no pace record and no connection to cap, so it is as written could-not-check. With one Major and no Critical the verdict is READY, but the pace and cap rule for a not-yet-existing connection should be settled before code generation.
