# U8 installation runbook: the runtime arrangement (Workflow 20)

Run once, in person, as an administrator of this Mac, before the first migration dry run
(BR6.11, BR8.11). It is run at the Operation stage, with your decisions. The installer is
the arrangement's one idempotent program; it waits on every step that needs your eyes or
a login, and records each step's name and outcome only.

## Before you start

- The release is staged on this Mac at `/Library/DocSuri/release/` (its own Python
  environment; see the release runbook). The installer's settings are the root-owned
  `/Library/DocSuri/control/installation.json`, which holds no secret.
- v1 keeps serving at `docsuri.rvnnt.dev`. It is unavailable only during step 10's
  restart, and its model calls pause only while step 5 switches the model runtime.
- Keep your password manager open: step 8 asks you to save the backup volume's new
  passphrase.

## 1. See the plan (changes nothing)

```bash
sudo -k /Library/DocSuri/release/ops/bin/docsuri-installer plan
```

It lists every change of the seven phases, each with its difference, and changes
nothing. Read it through. Nothing below runs until you run `apply`.

## 2. Apply

```bash
sudo -k /Library/DocSuri/release/ops/bin/docsuri-installer apply
```

The phases run in order; each checks its own result before the next starts. A phase
that fails stops the installer there; running `apply` again changes nothing that is
already in place. The installer refuses to run when the environment holds `PYTHON*`,
`DYLD_*` or `LD_*` variables, or when it does not run as root.

Workflow 20's steps, as the installer runs them:

1. **Accounts.** The service, scheduler, database, models and tunnel accounts, each
   non-login, with no shell and no home. The backup account already exists.
2. **Runtimes.** Root-owned PostgreSQL 16.14, the model runtime (Ollama), the tunnel
   (cloudflared) and the release's Python, each checked against its publisher's checksum
   and with `otool -L` (programs and libraries load only from their own folder and
   system paths). pgvector is the pinned 0.8.7.
3. **Folders and the database.** Folders with their owners and modes; `/Library/DocSuri/`
   and OrbStack's data folder excluded from Time Machine; the database job, which
   initialises v2's instance (SCRAM only, loopback only, private socket); every owner's
   roles, the disposable-databases role, and the scheduler's, backup agent's and operator
   tool's logins. Each password is generated by root straight into its holder.
4. **Rule files.** The packet filter's rules (not yet enabled), the tunnel's three
   registered configurations, the launch job definitions and the fixed-command rules.
5. **The model runtime**, moved without leaving v1 without its models: APFS clones of
   every pinned model's files, verified against the release's pins, then the system job.
6. **The tunnel**, moved without a gap (the checklist items below).
7. **The packet filter** enabled through its boot job.

typed. Declining stops the installer at that item.

### The keyring start (phase 7, last)

After `first-rehearsal-database`, v2's first start has created the verifier key in
`profile/verifier-key/` and the search cursor key in `profile/cursor-key/`, and no
account exists yet. The installer then starts the account keyring once (your decisions
of 2026-10-24 and 2026-10-25, "Start it at install, U8 snapshot"):

1. It stops v2's three roles through the operator tool's in-person service control, so
   PlatformControl holds each stop's receipt: it runs `echo '{}' |
   /Library/DocSuri/release/.venv/bin/python -I -m docsuri_ops.u8_platform service stop
   <label> --production` as your login account, once per label, and you authenticate in
   person. Each run asks for your password three times, each through `sudo -k`:
   - the release of the operator tool's PlatformControl login
     (`docsuri-credential-release platform`);
   - the ledger copy the run reads (`docsuri-ledger copy`);
   - the stop itself (`docsuri-service-stop <label>`; in step 3, `docsuri-service-start
     <label>`).

   The installer waits up to 11 minutes for each run (three minutes for each of the
   first two prompts, plus the run). The third prompt has less: the stop or start runs
   inside PlatformControl's bounded effect, whose deadline is 120 seconds, and the
   driver ends the program at 115 seconds (`program_bound`), for that prompt and the
   program together, so answer it within about a minute and a half. A later answer
   fails that control (`program-timed-out`); the installer then treats it as a failed
   stop or start (below).
   Before a run binds its receipt, the operator tool settles any earlier service control
   of that label left unresolved (an interrupted run), so you never need to clear one by
   hand.
2. It runs `docsuri-production-tool control-key-start` as the service account. That
   word starts the control keyring with U2's own rotation (a new active key, the start
   marker, the verifier-derived key kept for reading only), then writes U8's keyring
   snapshot under `profile/control-keys/`: the keyring alone, never the verifier.
3. It starts the three roles again the same way (`service start <label>`), whatever the
   word answered. A start that fails is recorded in the installation log and kept in
   `control/keyring-start-unstarted.json`: the phase fails, `verify` fails while the
   record is there, and the next `apply` starts each role it names (the same in-person
   start, the same three prompts), removing the record once every role is running.

The installation log records the snapshot's digest and generation, which key recovery
needs, and no key material. From then on every sign-in secret production holds uses the
started key, so a later verifier replacement neither blocks on them nor loses them. A
second `apply` finds the snapshot in place and does not start the keyring again; it
changes something only when a role is still recorded as unstarted, which it starts. The
installation is not verified until the keyring is started and every role is running.

## 4. Verify, and what it records

```bash
sudo -k /Library/DocSuri/release/ops/bin/docsuri-installer verify
```

It runs the installation's own checks and the isolation check (BR6.12). Among them, the
scheduler's three grants in `docsuri_v2_platform` are read and compared with the ones
this release defines: a grant that is missing, revoked or holds another scope or
operation fails `verify` (`platform-grant-drift:<grant>`). Each store login's binding is
read back too: a login unbound or bound to another actor, or a reader login still in
the runtime role, fails `verify` (`store-login-unbound:<kind>`), and `apply` on such an
install binds each login to its recorded actor and takes the reader out of the runtime
role (phase 3's `store-logins` change). The arrangement counts as
installed only when every step is done and every item passes; only then can a migration
dry run start (BR8.11).

What is recorded, and where:

- **The installation log**, `profile/evidence/installation-log.jsonl`: one JSON line per
  step, with only registered fields (a fixed key, a path, a version, a count or a
  digest), so it never holds a password, passphrase, token or certificate content.
- **The arrangement manifest**, `control/arrangement-manifest.json`: the digest of every
  file in place, written after every run, whichever way it ended. The isolation check
  compares against it.
- **The isolation evidence**, read directly by the migration tool at every phase
  boundary.

## 5. The production tool's settings words

Each runs in person as the service account, reads bounded JSON on standard input, and
writes its file atomically at mode 0600. None prints a value, and the installation log
names only the word:

```bash
sudo -k -u _docsuri_v2 /Library/DocSuri/release/ops/bin/docsuri-production-tool <word>
```

| Word | What it does |
|---|---|
| `export-settings` | Writes `real-export.json` (`runId`, `activationDestinationId`, `freeTerms`); takes effect at the next start. |
| `provider-environment` | Writes `private-environment.json` with any of the Google, ORCID and Resend credentials and the two senders; each secret has at least 16 characters. Providers are configured at the next start. |
| `research-review` | Runs the fixed research review set on three ready versions you name, on the production model runtime, and writes `evidence/reviews/research-<12 hex>.json` for your decision. Each injection probe records only whether the answer equals the injected word and whether it holds the system rule's marker; one probe injects through a source excerpt. |
| `readiness-evidence` | Records the reviewed real-model evidence marker by purpose (`{models, purposes}`). `research` is refused unless its digest names a review you read. |
| `control-key-recovery` | Restores a missing keyring record and start marker from U8's keyring snapshot, by its exact digest and generation (from the installation log). It refuses another folder, a missing snapshot or a divergent current file before writing, and never writes the verifier. |
| `replace-verifier-key` | Replaces the verifier key and ends every session and outstanding proof. The keyring snapshot stays valid afterwards. |
| `replace-cursor-key` | Replaces the search cursor key in `profile/cursor-key/`, or creates it when it is missing. It takes no input. Open search and job-list pages then restart at their first page (`open-cursors-restart`). Unlike the words above, it runs only while v2 is stopped (below). |

### Replacing the search cursor key

`replace-cursor-key` is refused while any of v2's three roles runs
(`cursor-key-replace-refused`, detail `v2-running`), and then writes nothing:

1. Stop v2's three roles (`service stop <label>`, as in phase 7's keyring start: three
   password prompts for each label).
2. Run `docsuri-production-tool replace-cursor-key`.
3. Start the roles again (`service start <label>`).

Open search and job-list pages then restart at their first page.

## 6. Changing a production password

A production password changes only in person, together with its roles' SCRAM verifiers,
through the installer's fourth word. Root generates each new password, computes its
verifier itself (the database never receives a password), sets the verifiers in one
transaction, rewrites the holder, reads it back, checks that each role logs in with its
new value and, for the scheduler, restarts the standing job.

**Apply first.** The word arrives in the sudo rules only with an in-person
`docsuri-installer apply` (the arrangement version stays 1, so no release installs the
new line). On a Mac installed before this release, run `docsuri-installer apply` in person
once before the first change. Until then the word runs under your general sudo use; the
`sudo -k` below still forces the password prompt, and the program's own root check and
its check that the account sudo authenticated is the installed operator are its gates.

```bash
echo '{"login": "<holder>"}' | sudo -k /Library/DocSuri/release/ops/bin/docsuri-installer change-password
```

| Holder | Roles | Where the passwords are kept | First |
|---|---|---|---|
| `owners` | the eleven `docsuri_<owner>` logins | `profile/owner-credentials.json` | stop v2's three roles |
| `platform-reader` | `docsuri_platform_reader` | `profile/platform-reader.json` | stop v2's three roles |
| `scheduler` | `docsuri_scheduler`, `docsuri_platform_scheduler` | `scheduler/credentials.json` | not during a scheduled backup or verification |
| `backup-agent` | `docsuri_backup_agent` | `backup-agent/v2-login` | not during a scheduled backup or verification |
| `operator` | `docsuri_operator` | System keychain item `docsuri-v2-operator` | not during a release command, a recovery or a migration run |
| `restore` | `docsuri_restore` | System keychain item `docsuri-v2-restore` | not during a release command, a recovery or a migration run |
| `platform-operator` | `docsuri_platform_operator` | System keychain item `docsuri-v2-platform` | not during a release command, a recovery or a migration run |
| `provisioner` | `platform_control_provisioner` | `control/platform-provisioner.json` | nothing |

For `owners` and `platform-reader`, stop v2's three roles first and start them again
after, as in "Replacing the search cursor key" (§ 5): `service stop <label>` for each of
`org.docsuri.v2.host`, `org.docsuri.v2.workers` and `org.docsuri.v2.scheduler`, the
change, then `service start <label>` for each. The ledger's standing job and the root
isolation check also read the reader's file at each run; one that reads it in the
seconds of the change meets a refused login for that run only.

**The answer.** One JSON line. Done: `ok` true, the holder's `roles`, the `holder` (its
path under `/Library/DocSuri` or its keychain item) and the `consequence`:

| Consequence | Meaning |
|---|---|
| `v2-reads-them-at-its-next-start` | v2 reads the new passwords when you start its roles again. |
| `standing-job-restarted` | The standing job was restarted and reads the new passwords. |
| `read-at-the-agents-next-run` | The backup agent reads its new login at its next run. |
| `read-at-the-next-in-person-use` | The next in-person release of that login uses the new value. |
| `read-at-the-next-installer-run` | The next installer run reads the new provisioner password. |

Refused or failed: `ok` false with `reason`. Refused before anything changed:
`input-too-large`, `input-not-json`, `input-not-an-object`, `input-field-refused`,
`in-person-actor-refused`, `authorities-file-refused`, `not-the-installed-operator`,
`login-outside-its-set`, `arrangement-change-in-progress`, `v2-running`,
`scheduled-work-running`, `release-run-active`, `release-run-marker-stale`,
`release-run-lock-unreadable`, `recovery-under-way`, `migration-under-way`,
`ledger-unreadable`, `holder-missing`, `holder-refused`. Failed with nothing changed:
`verifier-not-set`. Failed partway:

- `holder-not-rewritten`: the roles hold their new verifiers and the holder its old
  passwords (or the keychain item did not read back as written), so their logins fail.
  Run the same command again; it sets new values in both.
- `login-check-failed`: a role did not log in with its new value. Run the same command
  again.
- `standing-restart-failed`: the change holds, but the standing job was not restarted.
  Run the same command again, which changes the scheduler's passwords once more and
  restarts the job.

`arrangement-change-in-progress` means another arrangement change (an installer run), or
another password change, holds the work-under-way marker. After an interrupted run (a
power loss, a killed process) the marker stays until its hour passes (60 minutes from the
run's start). Before you run the same command again, check what the interrupted run
reached: its line in `control/password-changes.jsonl`, the holder, and the roles' logins.

An answer that also names `unrecorded` changed (or refused) as it says, but could not
write one of its evidence lines.

**The evidence.** Each run writes one line to the root-owned audit record
`control/password-changes.jsonl` and one to the installation log: phase
`password-change`, the holder's key, the outcome, its reason, the count of roles changed
and the account sudo authenticated (`actor`). Neither holds a password, a digest or a
length of one. The root record is the evidence, since the installation log lies in the
service account's folder.

**Not changed by this word**, because none is a role of v2's instance:

- v1's read-only login, which the backup agent keeps beside its v2 login: it changes in
  v1's data plane.
- The provider secrets: through `docsuri-production-tool provider-environment` (§ 5).
- The backup volume's passphrase: in person, on the volume itself, in the System keychain
  item `DocSuri_Backup` and in your password manager.
- The tunnel's credentials: by creating new credentials for the tunnel, as the installer's
  tunnel phase does.

## If something goes wrong

- A runtime whose programs load anything from a folder another account can write is not
  used; another root-owned source replaces it.
- Phase 2 stops with `runtime-program-missing:pgvector`, or `runtime-file-missing:pgvector`:
  pgvector's build left its library, or its control file or install script, somewhere other
  than the paths this release pins in the PostgreSQL runtime's folder (`lib/vector.dylib`,
  `share/extension/vector.control`, `share/extension/vector--0.8.7.sql`). Nothing after
  phase 2 has run. Note where the build put them. The corrected pin comes in a new release,
  and `apply` with it finds the built runtime and goes on.
- A cloned model file fails verification: the clones are deleted and nothing else
  changes. Pull the model again into your home folder before repeating step 5.
- The model runtime's job does not serve at the usual address, or reports a digest other
  than the pin: it is stopped and your login account's runtime starts again from its
  kept definition, so v1 gets its models back.
- A step fails before the hostnames' routes move: the old tunnel still serves v1; repeat
  the step. The routes move but the new tunnel does not serve: move them back; the old
  tunnel is deleted only once the new one serves.
- v1 does not answer after the restart: the maintenance notice stays; repair v1 from its
  checkout before routing back.
- `control-key-start` fails (`control-key-start-failed:<reason>`): v2's roles are started
  again and nothing else changes. Fix the reason and run `apply` again; a start cut short
  between the rotation and the snapshot is completed by the next run, which takes only
  the missing snapshot.
- A v2 start is refused with `cursor-key-missing-with-accounts`: accounts exist and the
  search cursor key in `profile/cursor-key/` is missing, so the start does not make one
  on its own. Follow "Replacing the search cursor key" in § 5 (stop the three roles, run
  `replace-cursor-key`, start them again). A rebuild after this Mac is lost always meets
  this, since no key is in a backup.
