### Resolution and Architectural Evidence

- **R-01:** `functional-spec.md` WF2's T1-to-T2 recovery paragraph, line 47, explicitly includes NOT_STARTED records in recovery scans, permits the creator/replay/recovery actor to compete for one guarded T2 first-send claim, and provides atomic no-send failure/release against competing claims. T2/T8 preserve current-job checks; SENDING/UNKNOWN cannot grant a second send. `rules.md` BR1.7, line 66, agrees. Numeric scheduling remains assigned to NFR Design rather than being mistaken for an already implemented recovery mechanism.
- **R-02:** WF1 steps 3–5, lines 36–38, reserve supersession before asynchronous hashing and recheck owner/context/revision before any storage or memory publication, without an intervening asynchronous yield. A stale completion writes nothing; returned-job persistence uses the same guard. BR1.5 agrees. Tracing A/B completion in either order and an owner change during hashing no longer permits A to overwrite B. Genuine storage failure still returns a truthful memory-only outcome.
- **R-03:** The Legacy Compatibility Bridge, lines 61–74, distinguishes newly normalized keyless callers, terminal pre-migration jobs, active legacy work and unversioned messages referencing proven new authority. `SubmissionBinding.idempotencyKey` is optional for the keyless profile; `DurableJob.authorityVersion` distinguishes new authority. Missing legacy ledger/dispatch evidence never becomes an invocation grant. Active old work must be drained or isolated, and incompatible senders/workers must be excluded before exposure. The required compatibility fixtures and later operational proof are explicit. This Unit finding is distinct from the accepted upstream Contract Design timestamp-checker finding also named R-03.
- **R-04/R-05:** `entities.md` lines 160/178, 226–227 and 243, and `functional-spec.md` lines 175/183–184 agree: each tracking context or draft may have zero or one attempt, while an attempt may have zero or multiple referring contexts/drafts over time. WF1 step 1 permits the initial editable draft without hashing, persistence-record fabrication or submission. The passed interaction specification's known-job/no-original branch remains query-only. The updated validator checks the actual optional fields and both ER endpoints, not merely relationship names.
- **Corrected C2:** The shared Reproducibility definition requires exactly string `code` and `data` (`shared/dtos/summarization.schema.json` lines 94–109); the existing SummaryDraft/DTO supplies that object (`models.py` lines 243/340). `entities.md` prepared-content constraints, BR2.3/BR3.2/BR5.1 and WF3 step 6/WF5 step 4 now require exact values without flattening, coercion or invented defaults. Malformed capture maps to safe FAILED; malformed stored content is unavailable only after ownership/state/known-expiry predicates. The same rules retain bare DocModel translation and final prepared personalization.
- **Preserved authority/read boundaries:** T5 preparation and T6 terminal publication remain separate commits; only T6 advertises a result and initializes fixed expiry. T7 rechecks the live fence/lease against renewal, and T8 prevents resurrection. The query path preserves 401 → indistinguishable missing/not-owned 404 → owned non-COMPLETED 409 → owned known-expired 410 → permanent unavailable 422 or transient store failure 503. Neither successful nor failed/retried reads have generation/enqueue/command capability. Component invocation dependencies in the passed catalogue are acyclic; the intentional optional job/result data-reference cycle is sequenced by T1 then T5 within one owner, not a circular service dependency.
- **Acceptance allocation:** Checked the map against the passed Unit/story allocation and the resolving `inception/user-stories/stories.md`.
